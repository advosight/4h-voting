# Phase 02.1 Plan 03: Frontend Event Management UI Summary

**Goal:** Give admins a way to see, switch, and archive the active event from the app UI, and make every judge's and admin's already-open screen refresh in place — no browser reload — the moment the active event changes.

**One-liner:** Frontend event management UI with EventContext, EventSelector dropdown, ArchiveEventDialog confirmation, and real-time in-place refresh via React key-driven remounting.

## What Was Built

### Task 1: EventContext + EventSelector (Tracer)

**EventContext.tsx** — React Context for app-wide event state management
- Exposes `activeEvent`, `activeEventId`, `loading`, `error`
- Provides methods: `refetchActiveEvent()`, `listEvents()`, `switchActiveEvent(eventId)`, `archiveAndCreateEvent(name, date)`
- Sets up `onActiveEventChangeSubscription` on mount for real-time updates
- Follows ResponsiveContext pattern exactly (createContext, useContext guard, Provider wrapper)
- GraphQL operations: `getActiveEventQuery`, `listEventsQuery`, `onActiveEventChangeSubscription`
- Handles unauthenticated page loads gracefully (returns null activeEvent, not error)

**EventSelector.tsx** — Admin-facing event dropdown + judge-facing read-only display
- Displays active event name as a MUI Chip (visible to all authenticated users)
- For judges: read-only chip only, no controls
- For admins: 
  - Dropdown menu to select and switch to any event via listEvents
  - Confirmation dialog on switch (shows target event name)
  - Archive & Start New Event button (delegates to ArchiveEventDialog)
- Mobile-optimized: icon-only menu on small screens, full labels on desktop
- Mounted in AppLayout's Toolbar between page title and sign-out button

### Task 2: ArchiveEventDialog + App.tsx Remount Strategy

**ArchiveEventDialog.tsx** — High-ceremony confirmation for archival
- Displays current event name, cat count, and total score count (fetched on open)
- Accepts new event name (required) and new event date (required)
- Warning message explains irreversibility and restore path
- Calls `archiveAndCreateEvent(name, date)` mutation from EventContext
- Disables submit button until both fields populated
- Shows loading state during submission, disables inputs
- Closes on success (relies on onActiveEventChange subscription to refresh state)
- Integrated into EventSelector via archive button

**App.tsx Restructure** — Real-time in-place refresh via key-driven remounting
- Wrapped entire app with `EventProvider` (outermost layer after root)
- Created `AppContent()` component that calls `useEvent()` to read `activeEventId`
- Added `key={activeEventId}` to:
  - `<AppLayout>` element (dashboard, reports, leaderboards, user management)
  - `<ScorePage>` (cage scoring route)
  - `<CageScorePage>` (cage scoring route)
  - `<ClassScorePage>` (both /class-score/:catId and /class-score/cage/:cageNumber variants)
  - `<FitShowScorePage>` (both /fit-show-score/:catId and /fit-show-score/cage/:cageNumber variants)
- Deliberately left unkeyed (will not remount on event change):
  - Public routes: /vote/:catId, /tv-mode, /participant-score/:participantId, /participant-class-score/:catId, /accept-invite
  - Admin utility: /sign/:catId (out of scope per RESEARCH.md Assumption A3)
  - Class score management: /admin/class-score/:classScoreId (utility, not user-facing scoring)

**Remount Strategy Effect:**
- When admin switches active event via EventSelector, `activeEventId` changes
- React detects key change on AppLayout and judge-facing pages
- Each keyed component is fully unmounted and remounted
- Mount-time `useEffect` data fetches re-run automatically
- Subscriptions re-established with new event context
- All nested components see fresh data for the new event
- No browser page reload required — seamless in-place refresh

## Decisions Made

**D-20 (Claude's Discretion — Data consistency strategy during eventId updates):** 
Implemented as React `key`-driven remount rather than per-component subscription-argument filtering. Rationale:
- Single source of truth: `EventContext` is the only place `activeEventId` is managed
- Matches this codebase's established "on event → full reload" idiom (RESEARCH.md Pattern 3)
- Simpler to reason about: "key change → unmount → remount → fresh mount data fetch"
- Avoids per-component boilerplate: each page doesn't need subscription parameter logic
- Explicit scope: only keyed routes remount; public routes are not affected
- Tested and verified: all 18 component tests pass, confirming isolation and correct behavior

**D-21 (Claude's Discretion — UI placement and design for event selector):**
- Placement: AppLayout Toolbar, between page title and sign-out button (always visible to authenticated users)
- Design: 
  - Read-only chip for judges (context awareness without controls)
  - Admin dropdown menu with switch/archive options
  - Mobile-optimized: icon-only on small screens
- Rationale: Toolbar is the navigation centerline (every page passes through it); placement ensures visibility without dedicated page real estate

<objective>
Roll the `eventId` field created in 02.1-01 out across the four existing data types (Cat, Score, ClassScore, FitShowScore) and their audit trails: stamp it server-side on every create, filter it into every full-table Scan-based list/lookup, and backfill it onto every record that already exists in production. This is the part of the phase that actually makes archiving/switching meaningful — without it, every event would see every other event's data.

**Design decision (Claude's Discretion — "GraphQL mutation/query design for event switching"):** No `eventId` argument is added to any existing Query field (listCats, getScoresByCat, listAllFitShowScores, etc.) and no frontend query call site changes are required by this plan. Every list/lookup resolver instead calls `getActiveEventId()` (from 02.1-01) itself and filters/stamps against whatever the SETTINGS/ACTIVE_EVENT pointer currently says. This fully satisfies D-06/D-07/D-09 ("when eventId changes, all GraphQL queries ... update to filter by the new active eventId" — because the server always resolves "active" fresh on every call, no client ever needs to pass an eventId) while avoiding a rewrite of the ~29 files with inline GraphQL operation strings RESEARCH.md flags as this phase's widest risk surface. Plan 02.1-03 layers the live-refresh UX (subscription + remount) on top of this.

**Scope note on cage-based lookups:** `getScoresByCage` (scoreDataAccess.ts) and `getClassScoresByCage` (classScoreDataAccess.ts) both internally Scan the `CAT#` partition filtered only by `cageNumber` to find a catId, then delegate to `getScoresByCat`/`getClassScoresByCat` — this is RESEARCH.md's Pitfall 3 exactly (cage numbers are reused year to year). `getFitShowScoresByCage` is presently unimplemented (`throw new ValidationError('not yet implemented')` in fitShowScoreResolver.ts) and is explicitly left unimplemented by this plan — there is nothing to eventId-filter in a function that already errors, and implementing it is not required by any locked decision.

Purpose: Make every write and every read of existing contestant/score data event-scoped, so archiving genuinely isolates one contest's data from the next.
Output: eventId stamped and filtered across resolver.ts, scoreDataAccess.ts, classScoreDataAccess.ts, fitShowScoreDataAccess.ts (+ their *Resolver.ts callers), schema.graphql, and a runnable backfill script.
</objective>

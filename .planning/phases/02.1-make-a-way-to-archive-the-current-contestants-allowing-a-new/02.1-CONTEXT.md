# Phase 02.1: Make a way to archive the current contestants, allowing a new event to take place - Context

**Gathered:** 2026-08-31
**Status:** Ready for planning

## Phase Boundary

Create a system for managing multiple 4-H events within the same application. Admins can archive the current contest (all cats and scores), start a fresh event for judging, and switch back to any previous event at any time. Judges always work in whichever event the admin has marked as active.

## Implementation Decisions

### Data Archiving Model
- **D-01:** Archive scope includes all cats/participants AND all scores (cage, class, fit & show) from the current event. Audit trails are archived as-is (unchanged).
- **D-02:** Do NOT archive user accounts or role/permission data — these persist across events and are managed centrally.

### Storage Architecture
- **D-03:** Use Event ID partitioning — add an `eventId` field to all data tables (Cat, Score, ClassScore, FitShowScore, ScoreAuditEntry, ClassScoreAuditEntry, FitShowScoreAuditEntry). This allows multiple events to coexist in the same database.
- **D-04:** All existing tables remain unchanged except for the addition of `eventId`. No separate archive tables; archived data lives in the same tables with a different eventId.

### Event Identity & Switching
- **D-05:** Introduce an Event record type (ID, name, date, status, archived_at, archivedBy) to represent each contest/event. Admin sets which eventId is "active" via a config/state management mechanism.
- **D-06:** Admin actively selects the current event — not automatic based on timestamps. When an admin switches the active eventId, the system updates in real-time.
- **D-07:** Real-time query switching — when eventId changes, all GraphQL queries/subscriptions update to filter by the new active eventId. Judges' screens update in place (no page reload required).

### Event Workflow
- **D-08:** "Archiving" = creating a new Event record with a new eventId and copying all current cats/scores to that new eventId. The original event becomes inactive but remains fully queryable.
- **D-09:** "Switching" = admin selects a different eventId to become active. All subsequent queries use that eventId. Users remain on the same page with data refreshing to show the switched event.
- **D-10:** No selective restore — only full event switches. When switching to a previous event, judges work with that event's complete cat/score dataset as it was at the time of archival.

### Audit & Accountability
- **D-11:** Log the archival action itself (who archived, when, which eventId). This creates an audit trail at the Event level.
- **D-12:** Existing score audit trails (scoreAuditEntry, classScoreAuditEntry, fitShowScoreAuditEntry) already track score changes. These are included in the archived eventId as-is.

### Claude's Discretion
- GraphQL mutation/query design for event switching (how does the API communicate the active eventId?)
- UI placement and design for event selector (dropdown, sidebar, dashboard, etc.)
- Data consistency strategy during eventId updates (transactional requirements)
- User experience for warning/confirming archival

## Existing Code Insights

### Reusable Assets
- **Real-time subscriptions via AppSync** — already in place. Can extend to filter by eventId.
- **Audit trail infrastructure** — Score, ClassScore, and FitShowScore types already have audit entries. These patterns carry to the Event archival logging.
- **Leaderboard components** — `FitShowScoreLeaderboard` and related components already filter by catId and cageNumber. Can extend to also filter by eventId.
- **Responsive Context** — judges' sessions maintain responsive state. Can add event subscription to update UI when admin switches events.

### Established Patterns
- **Real-time updates via AppSync** — All scoring uses WebSocket subscriptions; event switching should propagate the same way.
- **Last-write-wins conflict resolution** — Already implemented; applies within an event by catId + judgeId. No cross-event conflicts.
- **Optimistic UI updates** — Judges see immediate feedback; event switches should also be optimistic then confirm.

### Integration Points
- **GraphQL queries need eventId filters** — All list queries (listAllScores, listCats, etc.) must filter by active eventId.
- **Authentication/Role enforcement** — Existing ProtectedRoute checks judge/admin roles. Event access control (can judge see archived events?) to be determined during planning.
- **Subscriptions broadcasting** — When admin changes active eventId, broadcast to all connected judges via subscription update.

## Specific Ideas

- Archival should be a high-ceremony action — confirmation dialog showing event name, participant count, score count, and who is archiving.
- UI for event selector should always be visible to admins (maybe in top bar) so they know which event is active.
- Show a visual indicator (badge or banner) when a judge is viewing an archived event vs. the current active event.
- Restore from archive = just switching to that event's eventId; no data loss, fully reversible.

## Deferred Ideas

- **Event history timeline/calendar** — Not needed for Phase 02.1. Could be added in a future reporting/archive-management phase.
- **Bulk operations on archived events** — Exporting archived events as files, merging events, etc. — belongs in a future data management phase.
- **Archive cleanup/deletion** — Deciding when/whether to delete very old archived events — deferred to a future data retention policy phase.
- **Per-judge event visibility** — Whether judges can see/access archived events or only the admin-selected current event — decided by planning, not discussion.

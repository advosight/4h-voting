<objective>
Stand up the Event Management API: a new `Event` GraphQL type, a DynamoDB-backed `EventDataAccess` class, a new `eventResolver.ts` Lambda, and the CDK wiring to expose `getActiveEvent`, `listEvents`, `archiveAndCreateEvent`, `switchActiveEvent`, and `onActiveEventChange` on the AppSync API. This is the foundation Plan 02.1-02 (eventId stamping/filtering on existing Cat/Score/ClassScore/FitShowScore data) and Plan 02.1-03 (frontend event selector/archive UI) both build on.

**Design note — resolves RESEARCH.md's Open Question 1 / Assumption A1 (Claude's Discretion: "Data consistency strategy during eventId updates"):** "Archiving" (D-08) is implemented as a status-flip + pointer-move, NOT a physical duplication of every Cat/Score record on every archive action. Concretely: `archiveAndCreateEvent` (1) stamps `archivedAt`/`archivedBy` onto the CURRENT active event's own record, (2) creates a brand-new empty `Event` record, and (3) moves the `SETTINGS/ACTIVE_EVENT` pointer to the new event's id. No Cat/Score/ClassScore/FitShowScore item is copied or duplicated by this mutation — that would violate D-04 ("no separate archive tables ... same tables with a different eventId") and would double storage on every archive. D-08's "copying all current cats/scores to that new eventId" is satisfied instead by (a) new records created after the switch being stamped with the new eventId automatically (Plan 02.1-02), and (b) the one-time production backfill of today's untagged legacy data onto a bootstrap event (Plan 02.1-02, Task 3). This matches the phase goal's own framing — "start a **fresh** event for judging" — which is inconsistent with literally copying the old roster/scores forward. Flagging this explicitly per `<context_fidelity>` so it is auditable against the literal D-08 wording.

**Design note — Event.status is derived, not stored/mutated.** `status` ('active' | 'archived') is computed at read time by comparing an event's id to the current `SETTINGS/ACTIVE_EVENT` pointer, not written on every switch. This avoids a second source of truth that could drift from the pointer. `archivedAt`/`archivedBy` ARE persisted, stamped only by `archiveAndCreateEvent` (the actual archival action, per D-11) — a plain `switchActiveEvent` back to an old event does not touch them.

Output: `infrastructure/lambda/eventDataAccess.ts`, `infrastructure/lambda/eventResolver.ts`, updated `infrastructure/lib/schema.graphql` and `infrastructure/lib/cat-voting-stack.ts`, passing vitest coverage.

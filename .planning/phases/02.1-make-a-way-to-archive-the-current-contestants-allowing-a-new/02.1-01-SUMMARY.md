# Phase 02.1 Plan 01: Event Management API Summary

## What Was Built

Stand-up of the Event Management API — a foundation for multi-event support in the 4-H voting application. Admins can now archive the current contest, create a fresh event for judging, and switch between any previous event at any time. Judges always work in whichever event the admin has marked as active.

**One-liner:** Event GraphQL type, DynamoDB-backed EventDataAccess, eventResolver.ts Lambda, and CDK wiring for getActiveEvent/listEvents/archiveAndCreateEvent/switchActiveEvent/onActiveEventChange on AppSync.

## Design Decisions

### D-08 Implementation: Archiving as Status-Flip + Pointer-Move

**Design Note:** The literal wording of D-08 ("copying all current cats/scores to that new eventId") has been implemented as a status-flip + pointer-move strategy, NOT physical duplication of records:

- `archiveAndCreateEvent` (1) stamps `archivedAt`/`archivedBy` on the current active event's own Event record, (2) creates a brand-new empty Event record, and (3) moves the `SETTINGS/ACTIVE_EVENT` singleton pointer to the new event's ID.
- No Cat/Score/ClassScore/FitShowScore records are copied or duplicated on archive. Instead:
  - New records created after the switch are automatically stamped with the new eventId by resolvers (Plan 02.1-02)
  - The one-time production backfill (Plan 02.1-02, Task 3) migrates today's untagged legacy data onto a bootstrap event
- This satisfies D-04 ("no separate archive tables, archived data lives in the same tables with a different eventId") and matches the phase goal's framing ("start a **fresh** event for judging").

### Event.status is Derived, Not Stored

- `status` ('active' | 'archived') is computed at read-time by comparing an event's ID to the current `SETTINGS/ACTIVE_EVENT` pointer.
- No `status` attribute is persisted on the Event item — it is derived on every read.
- This avoids a second source of truth that could drift. `archivedAt`/`archivedBy` ARE persisted (audit trail per D-11).
- A plain `switchActiveEvent` back to an old event does not touch `archivedAt`/`archivedBy` — only `archiveAndCreateEvent` stamps them.

### Singleton Active-Event Pointer

Follows the existing **SETTINGS/VOTING_STATUS** pattern, now replicated as **SETTINGS/ACTIVE_EVENT**:

```
PK: 'SETTINGS'
SK: 'ACTIVE_EVENT'
Item: {
  activeEventId: 'event-123',
  updatedAt: '2026-09-02T20:00:00Z',
  updatedBy: 'admin-user-id'
}
```

No GSI required; read latency is a single GetCommand on a well-known key.

### Server-Side Event ID Resolution

- `getActiveEventId()` exported as a standalone helper for use by scoreResolver.ts / classScoreResolver.ts / fitShowScoreResolver.ts (Plan 02.1-02).
- Throws `SystemError('No active event configured')` if the pointer is unset — prevents downstream resolvers from silently writing undefined eventId onto new records.
- Client never supplies `eventId` on create mutations (security: a stale client tab could otherwise write into the wrong/archived event).

## API Surface

### Queries

- **getActiveEvent**: `Event | null` — Returns the currently active event, or null if none is configured.
  - Auth: `requireAnyRole(['admin', 'judge'])`
- **listEvents**: `EventConnection` — Returns all Event records with derived status (one active, rest archived).
  - Auth: `requireAnyRole(['admin', 'judge'])`

### Mutations

- **switchActiveEvent(eventId: ID!)**: `Event` — Moves the active-event pointer to a different event. Throws NotFoundError if the target event does not exist.
  - Auth: `requireRole('admin')`
  - Returns: The newly-active event with status='active'
- **archiveAndCreateEvent(newEventName: String!, newEventDate: String!)**: `Event` — Stamps archivedAt/archivedBy on the current active event, creates a new empty event, and makes it active.
  - Auth: `requireRole('admin')`
  - Returns: The newly-created active event with status='active'
  - Edge case: If no prior active event exists (first-ever call, pre-migration), creates the new event and sets it active without error.

### Subscriptions

- **onActiveEventChange**: `Event` — Fires when admin calls archiveAndCreateEvent or switchActiveEvent. All authenticated clients receive the updated event.
  - Broadcast: No filter arguments; every subscriber receives every event
  - Returns: The updated Event with its new status

## Threat Surface

### Mitigations Implemented

| Threat ID | Category | Mitigation |
|-----------|----------|-----------|
| T-02.1-01 | Elevation of Privilege (switchActiveEvent/archiveAndCreateEvent) | `requireRole(userContext, 'admin')` enforced server-side on both mutations, per existing pattern |
| T-02.1-02 | Repudiation (Event archival audit trail) | `archivedAt`/`archivedBy` stamped server-side from authenticated userContext on every archiveAndCreateEvent; never client-supplied |
| T-02.1-03 | Tampering (getActiveEventId consumers in Plan 02.1-02) | throws SystemError rather than returning undefined; prevents downstream resolvers from stamping undefined eventId |

No new security surface introduced beyond what D-05/D-06 scope requires.

## Architecture Notes

The Event Management API is built on proven patterns from this codebase:

- **Singleton config record pattern:** SETTINGS/ACTIVE_EVENT mirrors SETTINGS/VOTING_STATUS (already shipping in production)
- **Real-time subscription pattern:** onActiveEventChange mirrors onVotingStatusChange (no filter args, all clients receive)
- **Admin mutation auth pattern:** requireRole('admin') mirrors createCat/setVotingStatus
- **DataAccess class pattern:** EventDataAccess follows ScoreDataAccess constructor shape (not FitShowScoreDataAccess singleton)
- **Resolver handler pattern:** eventResolver.ts mirrors fitShowScoreResolver.ts try/catch/re-throw/AppError flow

No new external dependencies, no new AWS services, no new infrastructure patterns.

<objective>
Give admins a way to see, switch, and archive the active event from the app UI, and make every judge's and admin's already-open screen refresh in place — no browser reload — the moment the active event changes. This plan is purely additive (new files) plus two small, precise edits to App.tsx and AppLayout.tsx; it does not touch any of the ~24 existing files with inline GraphQL list-query strings, because 02.1-02 made every list/lookup resolver default to "whatever's currently active" server-side (no eventId argument needed on any existing query).

**Design decision (Claude's Discretion — "Data consistency strategy during eventId updates" / "UI placement and design for event selector"):** Real-time in-place refresh (D-07) is implemented as a React `key`-driven remount rather than per-component subscription-argument filtering. `EventContext` is the single source of truth for `activeEventId`; a new `AppContent` component (introduced inside App.tsx) reads it and passes it as the `key` prop on `AppLayout` and on each standalone judge-facing scoring page element. When `activeEventId` changes, React unmounts and remounts that subtree, which re-runs every nested page's mount-time `useEffect` data fetch and re-subscribes every nested subscription — matching this codebase's own established "on event -> full reload" idiom (RESEARCH.md Pattern 3), just applied once at the top instead of once per list component. Public/unauthenticated routes (`/vote/:catId`, `/tv-mode`, `/participant-score/:participantId`, `/participant-class-score/:catId`, `/accept-invite`) and the admin-only `/sign/:catId` utility page are deliberately left un-keyed and unaffected by event switches, per RESEARCH.md's Assumption A3 (public voting is out of scope for this phase).

**Design decision — "badge for archived event" idea (CONTEXT.md Specific Ideas).** Because switching the active event is global (D-09: it changes what *everyone* sees, not a personal per-admin browsing mode), there is no state in this app where one user is looking at an "archived" event while others see something else — whichever event is active is active for all. The underlying need (context awareness of which contest you're in) is met instead by EventSelector always displaying the active event's name, visible to every authenticated user at all times, not just on switch.

Purpose: Complete the phase's user-facing workflow — archive, start fresh, switch back — and satisfy the real-time, no-reload requirement.
Output: EventContext.tsx, EventSelector.tsx, ArchiveEventDialog.tsx, and the App.tsx/AppLayout.tsx wiring that ties them together.
</objective>

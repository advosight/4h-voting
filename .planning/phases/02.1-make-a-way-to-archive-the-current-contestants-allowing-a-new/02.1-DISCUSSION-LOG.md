## Scope of Archiving

**Question:** When an event is archived, which of these should be included?

| Option | Description | Selected |
|--------|-------------|----------|
| All scores | Cage scores, class scores, fit & show scores, and their audit trails | ✓ |
| All cats/participants | Cat records with their metadata (name, owner, breed, age group, cage number) | ✓ |
| User accounts & roles | Judge/admin accounts with their permissions at the time of archival | |
| Event metadata only | Just the event record itself (name, date, who archived it, timestamp) | |

**User's choice:** All scores + All cats/participants

**Follow-up - Audit Trail Handling:**
- **Question:** For the archived event's audit trails, which approach makes sense?
- **Options:** Archive as-is (unchanged) vs. Snapshot with metadata
- **User's choice:** Archive as-is — audit entries keep original judge names/timestamps unchanged

**Notes:** User prioritized keeping complete data snapshots (cats and scores) so events can be fully restored. User accounts are centrally managed and not archived with events.

---

## Archive Storage Model

**Question:** How should archived event data be organized in the database?

| Option | Description | Selected |
|--------|-------------|----------|
| Separate archive tables | Create ArchivedCat, ArchivedScore, ArchivedClassScore tables | |
| Event ID partitioning | Add eventId field to existing tables. Filter by eventId to show current vs. archived events | ✓ |

**User's choice:** Event ID partitioning

**Notes:** This choice fundamentally shapes the architecture — instead of moving data to separate tables, we add an eventId to all data records. This means archived and current data coexist in the same tables. Simpler querying and no data movement during archival.

---

## Event Identity & Switching

**Question:** How should the system identify the 'current' event that judges are scoring?

**User's choice:** Admin selects actively (not automatic)

**Follow-up - Switching Experience:**
- **Question:** When an admin switches to a different event, what should judges see?
- **Options:** Fresh page load (reload UI) vs. Real-time query switch (quiet switch, no reload)
- **User's choice:** Real-time query switch — judges' screens update in place without requiring a page reload

**Critical Clarification:** User noted that with eventId partitioning, we're not really "restoring" data — we're switching between existing events. This reframed the mental model: archive = create new event record; switch = set active eventId; restore = just switch back.

**Notes:** Admin has explicit control over which event is active. Judges work in whatever event the admin designates. Real-time switching means judges experience immediate data updates when admin changes the active event.

---

## Restoration Granularity

**Question:** When restoring from an archived event, what should be possible?

| Option | Description | Selected |
|--------|-------------|----------|
| Full event restore | Restore entire archived event as-is (all cats, all scores) | ✓ |
| Selective cat/score restore | Pick individual participants or scores to restore from archive | |
| Restore with conflict resolution | If current event has newer data for same cat, show conflict and let admin choose | |

**User's choice:** Full event restore (event switching, really)

**Notes:** With the eventId model, "restoration" is really just switching to a previous event's eventId. No data overwriting, no conflicts — all data is preserved in the database. Fully reversible.

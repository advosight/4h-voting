## User Constraints (from CONTEXT.md)

### Locked Decisions

**Data Archiving Model**
- D-01: Archive scope includes all cats/participants AND all scores (cage, class, fit & show) from the current event. Audit trails are archived as-is (unchanged).
- D-02: Do NOT archive user accounts or role/permission data — these persist across events and are managed centrally.

**Storage Architecture**
- D-03: Use Event ID partitioning — add an `eventId` field to all data tables (Cat, Score, ClassScore, FitShowScore, ScoreAuditEntry, ClassScoreAuditEntry, FitShowScoreAuditEntry). This allows multiple events to coexist in the same database.
- D-04: All existing tables remain unchanged except for the addition of `eventId`. No separate archive tables; archived data lives in the same tables with a different eventId.

**Event Identity & Switching**
- D-05: Introduce an Event record type (ID, name, date, status, archived_at, archivedBy) to represent each contest/event. Admin sets which eventId is "active" via a config/state management mechanism.
- D-06: Admin actively selects the current event — not automatic based on timestamps. When an admin switches the active eventId, the system updates in real-time.
- D-07: Real-time query switching — when eventId changes, all GraphQL queries/subscriptions update to filter by the new active eventId. Judges' screens update in place (no page reload required).

**Event Workflow**
- D-08: "Archiving" = creating a new Event record with a new eventId and copying all current cats/scores to that new eventId. The original event becomes inactive but remains fully queryable.
- D-09: "Switching" = admin selects a different eventId to become active. All subsequent queries use that eventId. Users remain on the same page with data refreshing to show the switched event.
- D-10: No selective restore — only full event switches. When switching to a previous event, judges work with that event's complete cat/score dataset as it was at the time of archival.

**Audit & Accountability**
- D-11: Log the archival action itself (who archived, when, which eventId). This creates an audit trail at the Event level.
- D-12: Existing score audit trails (scoreAuditEntry, classScoreAuditEntry, fitShowScoreAuditEntry) already track score changes. These are included in the archived eventId as-is.

## Summary

This phase adds multi-event support to a **single-table DynamoDB app** (`cat-voting-table`, PK/SK design, `PAY_PER_REQUEST`, **no GSIs defined**) fronted by **AWS AppSync** (GraphQL, Cognito-User-Pool auth + API-key for public routes) and a React/Vite frontend using **aws-amplify v6.18.0**'s `generateClient()`. Every "list all" query in this codebase (`listCats`, `listAllScores`, `listAllClassScores`, `listAllFitShowScores`, `listFitShowScores`) is implemented as a **full-table `ScanCommand` with a `FilterExpression`** — there are zero Global Secondary Indexes anywhere in the stack `[VERIFIED: infrastructure/lib/cat-voting-stack.ts:38-46]`. This is the single most important fact for planning: adding `eventId` scoping is an attribute-and-filter-expression change, not a partition-key restructuring, which is exactly what D-04 already mandates ("existing tables remain unchanged except for the addition of eventId").

The codebase has **no generated GraphQL operations file** — 29 files independently define inline `query`/`mutation`/`subscription` template strings, and 34 files call `generateClient()`/`client.graphql()` directly `[VERIFIED: grep count across src/, this session]`. This means the eventId rollout touches every list/subscribe call site individually; there is no single client SDK layer to patch once. Plan accordingly — this is a wide, shallow phase, not a narrow, deep one.

The codebase already contains the **exact precedent pattern** needed for both the "active event" pointer and its real-time broadcast: `getVotingStatus`/`setVotingStatus` store a singleton config record at `PK: 'SETTINGS', SK: 'VOTING_STATUS'` `[VERIFIED: infrastructure/lambda/resolver.ts:410-437]`, and `DashboardPage.tsx` subscribes to `onVotingStatusChange` and updates local React state directly on push, with no page reload `[VERIFIED: src/pages/DashboardPage.tsx:106-108,231-239,309-323]`. The recommended `activeEvent` pointer and `onActiveEventChange` subscription should be a structural copy of this existing, working pattern.

**Primary recommendation:** Store Event records the same way every other entity is stored (`PK: EVENT#<id>, SK: METADATA`), track the active pointer as a `SETTINGS` singleton exactly like `VOTING_STATUS`, stamp `eventId` onto new records **server-side** (never trust a client-supplied `eventId` on create mutations), and propagate switches via a new `onActiveEventChange` subscription with no filter arguments (all clients receive it) while filtering per-event data feeds via AppSync's built-in basic subscription-argument filtering (max 5 args, equality, AND-only `[CITED: docs.aws.amazon.com/appsync/latest/devguide/aws-appsync-real-time-enhanced-filtering.html]`).

### Pattern 1: Singleton config record for the active-event pointer
**What:** A single DynamoDB item at a well-known key holds the currently active `eventId`.
**When to use:** Exactly this phase's D-05/D-06 requirement ("admin sets which eventId is active via a config/state management mechanism").
**Example (existing, verified pattern to copy):**
```typescript
// Source: infrastructure/lambda/resolver.ts:410-437 (read this session)
async function getVotingStatus() {
  const result = await docClient.send(new GetCommand({
    TableName: process.env.TABLE_NAME,
    Key: { PK: 'SETTINGS', SK: 'VOTING_STATUS' },
  }));
  return { isActive: result.Item?.isActive ?? true };
}

async function setVotingStatus(isActive: boolean) {
  await docClient.send(new PutCommand({
    TableName: process.env.TABLE_NAME,
    Item: { PK: 'SETTINGS', SK: 'VOTING_STATUS', isActive, updatedAt: new Date().toISOString() },
  }));
  return { isActive };
}
```
Recommended new analog: `PK: 'SETTINGS', SK: 'ACTIVE_EVENT'`, `Item: { activeEventId, updatedAt, updatedBy }`.

### Pattern 2: Real-time broadcast of an admin toggle to all connected clients
**What:** A no-argument subscription that every client subscribes to; the client updates local state directly on push, no refetch/reload.
**When to use:** D-07 requires judges' screens to update in place with no reload when the admin switches events.
**Example (existing, verified pattern to copy):**
```typescript
// Source: src/pages/DashboardPage.tsx:106-108, 231-239 (read this session)
const onVotingStatusChange = `
```

**What:** List queries take an `eventId` argument; subscriptions trigger a full reload of that filtered list rather than pushing deltas.
**When to use:** Every "list all" / leaderboard / reports screen (`FitShowScoreLeaderboard`, `ScoreLeaderboard`, `ClassScoreLeaderboard`, `*Reports.tsx`, `*ScoringPage.tsx`).
**Example (existing pattern, verified — extend with eventId variable):**

### Anti-Patterns to Avoid
- **Trusting a client-supplied `eventId` on create mutations:** always resolve the active event server-side from the `SETTINGS/ACTIVE_EVENT` pointer inside the Lambda resolver before the `PutCommand`, never from `event.arguments.input.eventId`. A stale client tab left open across an event switch would otherwise silently write into the wrong (possibly archived) event.
- **Assuming `cageNumber` is a stable per-event identifier:** physical cage numbers are very likely reused across different 4-H events/years. `getCatByCage`, `getScoresByCage`, `getClassScoresByCage`, `getFitShowScoresByCage` all currently `Scan`/`Query` on `cageNumber` alone `[VERIFIED: infrastructure/lambda/resolver.ts:130-136]` — every one of these MUST also filter by `eventId`, or a judge could accidentally pull cage 12's score from last year's archived event.
- **Filtering only `JUDGE#`-partitioned queries and skipping `CAT#`-partitioned ones "because catId is already unique per event":** true today (Cats get fresh UUIDs each event under the current archiving model), but still add `eventId` to the `CAT#`-partition FilterExpression for defense-in-depth and because D-10 ("switch back to any previous event... complete cat/score dataset") implies old events' `CAT#` partitions must remain independently queryable and correctly attributed.
- **Building a delta-sync mechanism for the event switch:** the existing subscription idiom in this codebase is always "notification fires -> full reload", never incremental patching. Do not introduce a different sync strategy just for events; match the established pattern (Pattern 3 above) for consistency and lower risk.

## Common Pitfalls

### Pitfall 1: Forgetting that `Scan` + `FilterExpression` still reads (and bills) every item in the table
**What goes wrong:** Adding `eventId` to a `FilterExpression` does NOT reduce the RCUs consumed by a `ScanCommand` — DynamoDB still reads every item in the table before filtering. As archived events accumulate over multiple years, `listAllScores`/`listFitShowScores`/etc. will get progressively slower and more expensive even though each individual event's dataset stays small.
**Why it happens:** This app already uses full-table Scans for every "list all" operation with no GSI `[VERIFIED: infrastructure/lambda/fitShowScoreDataAccess.ts:487-495]`; adding eventId filtering is layered on top of that existing pattern rather than replacing it.
**How to avoid:** Acceptable for this phase given D-04's explicit "no restructuring" constraint and the app's small per-event data volume (a single 4-H contest, not a high-throughput SaaS). Flag as a documented tradeoff, and note that a `GSI` on `eventId` (or restructuring PKs to `EVENT#<id>#CAT#<id>`) is the natural follow-up if the table grows to many years of archived events.
**Warning signs:** `listFitShowScores`/`listAllScores` latency growing noticeably year over year; CloudWatch `ConsumedReadCapacityUnits` climbing even though score counts per event stay flat.

### Pitfall 2: A mutation resolver's GraphQL response must include the filtered field for AppSync basic subscription filtering to work
**What goes wrong:** If `createFitShowScore`'s resolver response doesn't include `eventId` (e.g., it's stripped before returning, or the GraphQL type doesn't expose it), AppSync's basic subscription-argument filtering silently fails to match — subscribers either get nothing or get everything, with no error surfaced.
**Why it happens:** AppSync's basic filtering matches subscription arguments against fields **in the mutation's actual response payload**, not against some separate filter you configure elsewhere `[CITED: docs.aws.amazon.com/appsync/latest/devguide/aws-appsync-real-time-enhanced-filtering.html]`.
**How to avoid:** Add `eventId: ID!` to the `Cat`, `Score`, `ClassScore`, and `FitShowScore` GraphQL types (not just the DynamoDB item), and ensure every `createX`/`updateX`/`finalizeX` resolver returns the full object including `eventId`.
**Warning signs:** Judges report the leaderboard "doesn't update live" after an event switch, but a manual refresh shows correct data — indicates the subscription connected but the filter never matched.

### Pitfall 3: `cageNumber` is not a stable per-event identifier
**What goes wrong:** `getCatByCage`, `getScoresByCage`, `getClassScoresByCage`, `getFitShowScoresByCage` all key off `cageNumber` alone today. Once two events share the same physical cage numbers (very likely for a recurring 4-H show), these queries will return a mix of current and archived-event data unless `eventId` is added to their filter.
**Why it happens:** `cageNumber` was designed as a within-event physical identifier, not a cross-event unique key `[VERIFIED: infrastructure/lambda/resolver.ts:130-136 — getCatByCage filters only on cageNumber]`.
**How to avoid:** Every cage-scoped query must gain an `eventId` argument (defaulting server-side to the active event) alongside `cageNumber`.
**Warning signs:** A judge scoring "cage 12" after an event switch briefly sees a stale participant name or score from a previous year before the correct data loads (or never sees the correct data if the bug ships).

### Pitfall 4: 29 inline GraphQL operation strings must each be updated individually — no single client SDK layer
**What goes wrong:** Because there's no generated/shared GraphQL operations module, it's easy to update the 5 leaderboard/report components and miss one of the 24 other files that also embed inline query/mutation/subscription strings (forms, scoring pages, admin pages) `[VERIFIED: grep count, this session — 29 files match `query X(`/`mutation X(`/`subscription X` patterns]`.
**Why it happens:** Every component authors its own GraphQL document string rather than importing from a shared source.
**How to avoid:** Before closing this phase, grep for every inline `query`/`mutation`/`subscription` template literal referencing `Cat`, `Score`, `ClassScore`, or `FitShowScore` fields and confirm each one either (a) passes `eventId`/relies on server-side defaulting, or (b) is deliberately event-agnostic (e.g., `getScore(id)` by unique ID) with a comment explaining why.
**Warning signs:** One scoring form or report screen silently keeps showing archived-event data after a switch while every other screen updates correctly.

## Open Questions

1. **Does D-08's "copying" mean physical duplication, or a tag/status change?**
   - What we know: D-04 says "no separate archive tables; archived data lives in the same tables with a different eventId," which strongly implies no duplication is needed for ongoing archive actions — new records simply keep getting stamped with whatever eventId is currently active.
   - What's unclear: D-08's literal wording ("copying all current cats/scores to that new eventId") could be read as requiring an active copy step on every archive.
   - Recommendation: Confirm with the user (or resolve during planning) that "archive" = (1) flip the current active Event's status to `archived` + set `archivedAt`/`archivedBy`, (2) create and activate a brand-new Event record, and (3) all *subsequent* new Cat/Score records get the new eventId automatically via the active-event pointer — with the "copying" language in D-08 referring only to the one-time production backfill of today's untagged data (see Assumption A1).

2. **Should public/unauthenticated routes respect the active/archived event boundary?**
   - What we know: `/vote/:catId`, `/tv-mode`, and `/participant-score/:participantId` are public routes that display Cat and score data by direct ID, independent of the judge/admin scoring flows this phase's decisions focus on.
   - What's unclear: CONTEXT.md doesn't address whether an old public vote link (e.g., shared on social media for a prior year's cat) should still resolve, or whether TV Mode should only ever show the currently active event.
   - Recommendation: Treat as out of scope for this phase's mutations (getCat/getVotesByDay stay ID-keyed and event-agnostic) unless the user confirms otherwise, but flag this explicitly to the user/planner as a gap in CONTEXT.md's Deferred Ideas list — it's neither an explicit decision nor an explicit deferral.

3. **Per-judge event visibility, deferred in CONTEXT.md but touching this phase's queries directly**
   - What we know: CONTEXT.md's Deferred Ideas explicitly lists "Per-judge event visibility... decided by planning, not discussion."
   - What's unclear: Whether judges can query/see archived events at all (e.g., for their own historical reference) or only ever see whatever the admin has marked active.
   - Recommendation: Default to "judges only ever see the active event" (simplest, matches D-06/D-07's framing of judges reacting to admin's active-event choice) unless the planner has reason to open read access to archived events for judges too. Admins should be able to view/switch to any event (D-10).
